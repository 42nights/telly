WHOOP data · catalog, not a connection

The NOOP-to-server link stays not connected. No board value is a WHOOP reading.

Every field NOOP collects from a WHOOP 5.0 / MG strap is in the exhaustive WHOOP capability catalog (reference only; it shows types such as {int} bpm, not readings). The typed contract for that catalog is #27. The live connection is #69 and #70, owned by @ayaangazali.

Confirmed BLE capability (NOOP, on the strap)
  • Heart rate, about 1 Hz, standard characteristic 0x2A37
  • R-R intervals in ms, every beat
  • Battery %, standard characteristic 0x2A19
  • 100 Hz motion, only during a user-started capture session
  • Double-tap and wrist on / off events
  • Per-second history arrives on sync, 90 s to 15 min late
Unavailable
  • NOOP → server: not_connected; no transport, ingestion, readings, zeros, or nudges
  • SpO₂: the strap sends no blood-oxygen value
  • Raw respiration: no rows from the 5.0 / MG; respiratory rate is only estimated from R-R
  • Recovery and skin-temperature deviation: need a baseline; not populated
Unvalidated data
  • Skin-contact flag and the possible SpO₂ byte
  • Skin-temperature conversion (catalog lists both ADC and raw ÷ 100; #27 resolves it)
  • MG ECG waveform: experimental, seen on one device
  • Strain above 21, accelerometer-saturated event, optical blocks, hardware step counter (not decoded)
Deferred hardware research
  • Buzz, stop, and double-tap without deleting the wake alarm: #38
  • Fall and breathing signal validation (no measured latency): #6
  • Optional Meta glasses adapter and display: #18, #19
  • HealthKit import: #47

Stability-first architecture

Why this web stack

The HUD and dashboard are interactive apps. Vite avoids an unneeded SSR server.

Why Effect 4

Keep typed service logic, schemas, and resource cleanup. Hono owns HTTP; do not depend on the unstable HttpApi module.

Why Node + Bun workspaces

Node has documented SpacetimeDB SDK support. Bun workspaces share packages across web, native, and server. Biome handles formatting and lint.

Why no SQL ORM

SpacetimeDB is already selected. Use its schema and generated bindings, not a second database.

Authentication

Use verified OIDC identities and family permissions in both API and database. SpacetimeAuth beta remains a release risk, not a waived check.

Release gate

Pin tested versions. Prove access control, reconnects, stale-data behavior, and alert delivery before calling the system reliable.

Why Hono now?

Stability changes the choice: Round 10 kept HttpApi. Round 11 prioritizes stability, so this plan replaces its unstable HTTP module with Hono.

One owner per boundary: Hono handles routes and middleware. Effect handles service logic and schemas. Validate requests and provider responses explicitly.

No hidden shortcut: Implement error-to-HTTP mapping, request cancellation, and runtime cleanup. Share endpoint schemas with clients; do not maintain competing validators.

Scope: this board records the approved plan. GitHub issues track implementation.

Alternatives and generator boundary

Next.js / TanStack Start: useful for SSR; no such requirement here. tRPC / oRPC: not required for the Hono HTTP boundary.

Bun runtime: viable; Node is the conservative SDK choice. Bun is the package manager only. Convex / Postgres: not selected because they replace or duplicate SpacetimeDB.

Better-T-Stack 3.44.2 has no Effect or SpacetimeDB preset. Generate the app workspace only; add the real service and database modules separately.

Required implementation gates.

Small tests, real risks

Keep access, stale-data, alert replay, and contract checks. Skip snapshot churn and tests that only copy the implementation.

Two requested gates

Sentrux enforces structural rules. Fallow checks unused code, copies, complexity, and import boundaries. Neither replaces the compiler or runtime smoke.

Fast, not weaker

Run independent groups concurrently. Build once. Cancel superseded runs. Keep native checks for native changes and release validation.

TypeScript: use strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, and noEmit for type-only checks. Extend the native framework configuration rather than replacing it.

Contracts: infer request, response, and error types from packages/contracts. Decode unknown JSON and native events. Do not use any, assertions, or suppression comments to bypass checks.

Sentrux: pin the binary and parser plugins. Start with max_cycles = 0 and no_god_files = true in .sentrux/rules.toml. No moving score target or automatically renewed baseline.

Fallow: pin 3.31.0. Configure all real entry points and six zones: web, native, server, contracts, db, and database module. Clients may import contracts, not server or db code.

Accuracy: keep generated bindings in the boundary graph, but exclude generated copies from duplicate and complexity checks. Review each narrow exception. Do not ignore all of packages/db.

No coverage quota: disable the estimated CRAP gate with health.maxCrap = 0. Keep compiler checks, complexity checks, and tests for behavior risks.

Startup: use one full Fallow scan per change while this repository is small. It needs no comparison worktree or baseline. Measure real CI before adding incremental machinery.

Proof: isolated Sentrux 0.5.7 and Fallow 3.31.0 checks accepted a simple graph and rejected an injected cycle.

Minimum behavior checks and build scope

Access: another family cannot read data or acknowledge alerts. Invalid tokens fail closed.

Data: malformed, stale, duplicate, or reordered samples do not create false reassurance or duplicate alerts.

Delivery: persist the alert and pending delivery together. Retry after interruption without losing work; keep sent and acknowledged separate.

Contracts: reject invalid external values and preserve units, source time, nullable fields, and error responses across the API.

No glasses: run every feature with no paired device and DAT unavailable. Cover camera markers, voice, chat, alerts, and reports.

Disconnect: remove glasses during a session. Phone capture, messages, and pending alert delivery must continue without data loss.

One runtime smoke: ingest a synthetic sample through the actual service and database, then observe the family alert. Fake providers do not prove real delivery.

Native: verify phone permissions and suspension for the core release. Verify DAT hardware separately before enabling the optional glasses adapter.

CI: cache by lockfile and tool version. Regenerate database bindings and reject drift. A stable final job must reject any failed or unexpectedly skipped prerequisite.

No hidden work: no model training, paid APIs, coverage collection, broad browser matrix, or duplicate build in ordinary checks. Release validation still checks real provider and hardware behavior.

Cloudflare setup and limits

Members: the account administrator invites teammates with only the roles and scope they need. Keep each login and MFA separate.

Worker secrets: read per-Worker bindings through env.GEMINI_API_KEY. Never use plaintext Wrangler vars for secrets.

Secrets Store: account-level secrets use a binding and asynchronous get(). The documented scopes are Workers and AI Gateway.

Permissions: Secrets Store Admin manages values; Deployer can bind them. CI needs Account Secrets Store Edit when deploying these bindings.

Local work: use separate development keys in ignored .dev.vars or .env files. Local bindings cannot read production Secrets Store values.

Trust: anyone who can deploy code using a binding can make that code read the secret. Limit deployment access too.

Existing Node / Python runtime · no Cloudflare binding

After building the planned server, run from the repository root:

chmod 600 apps/server/.env.local
node --env-file=apps/server/.env.local apps/server/dist/main.js

For a Linux deployment, provision the file privately under the service account first:

node --env-file=/run/secrets/telly.env apps/server/dist/main.js

The host or operator supplies the file; the command does not create secrets.

Existing environment variables override Node's env-file values. Remove stale injected values when rotating a file-based key.

In the planned apps/server/src/config.ts, validate and redact each required key with Effect 4:

import { Config, Schema } from "effect"

export const GeminiKey = Config.schema(
  Schema.RedactedFromValue(
    Schema.String.check(Schema.isMinLength(1))
  ),
  "GEMINI_API_KEY"
)

Load it with yield* GeminiKey during Effect startup. Missing or empty values fail configuration. Unwrap only for the provider call.

Redaction prevents accidental value display; it is not encryption. The process and host administrators can still access injected secrets.

Python workers read their own injected environment with os.environ. Do not pass the entire server key set to every worker.

GitHub setup, rotation, and agent access

Protect the deployment branch and environment. Run ordinary PR checks without provider keys; never run untrusted PR code with deployment secrets.

Record only key names, owners, and environment names in issues. Give agents scoped credentials; never put secret values in their prompts.

An agent that can execute commands with injected credentials can read them. Environment injection is not an agent security boundary.

Give each provider separate development and production keys where supported. Set scopes, quotas, and expiry. Revoke departing users' access.
